## Short description

Muse Recall is a local-first studio for building small browser applications with project memory you can inspect and correct. Remember the brief, bring image, voice and video references, and review each proposed change before approval. Keep the application, versions and decisions supplied to each generation together.

## What the beta does

Decisions persist with provenance, revisions and supersession. Bounded retrieval supplies active records to later work; correcting a decision retains its history. A review queue, timeline, relationship map and versioned export/import help inspect and move project memory.

HTML Studio stages each generation with preview, source and changes. Approval publishes the exact prepared bytes checked by syntax and load-time verification. Version history, rejection and ancestry-based rollback retain control. Seven source-pattern Guard families and revision-pinned screenshot review offer advisory evidence, not compliance certification.

The expanded beta adds image generation/editing, approved asset embedding, SAM cutouts, vision-proposed decision drafts, voice/video source playback, transcription and clip observations. Media inference uses separate server-side credentials. Seven shared application/MCP tools, REST APIs, durable jobs, backup/restore and operational recovery support local use.

## How Muse is used

The Muse Code CLI generates and modifies applications. Chat and coding model configuration can differ; separate media APIs handle images, segmentation, transcription and vision review. The memory engine, retrieval, source-pattern Guard and approval checks are deterministic infrastructure. Spark Open was a research provider, not an application provider.

## Evidence and boundaries

Phase 17 retained 480 pre-registered runs across two models and six fixed strata. Among usable runs, original-rule violations changed from 37/57 to 0/58 on Spark and 49/60 to 1/60 on Spark Open with retrieved memory. Eight Spark runs hit the time cap. Retyping the rule manually produced 0/58 and 0/60. These are fixed source-pattern tasks, not runtime safety or general correctness results, and they do not validate the newer media workflows. See [results](../hackathon-evidence/phase17/RESULTS.md) and [statistical correction](../hackathon-evidence/phase17/STATS_CORRECTION.md).

The three-minute demo combines retained live correction footage, current beta replays, actual provider media and labelled fixtures. The stale palette returned after memory correction; success required explicitly requesting current decisions. The release gate uses deterministic responses to test platform workflows. Separate live media records show successful examples. Neither establishes general generated-output quality.

Single-user beta, loopback by default, optional shared bearer access and no user accounts. One generated HTML file per application. Approval checks loading, not every interaction or design quality. The retained Palette Bench example still has open application findings and an unscored human quality sheet.
